# 微信旧链路与原生房间直连对比（2026-10-10）

修复后的直连中位数 **12.21 秒**，旧链路 **32.52 秒**，本轮降低 **62.5%**。两组各 10 条，全部由微信 API 接受、答复数字正确，用户确认手机实收；每条已接受发送记录均为一次。

## 条件与时间边界

- 同一账号、同一既有爱丽丝和相同网络配置；未修改模型设置。服务端实际模型 ID 未采集。
- 先测旧链路，再测修复后的直连；每条收到回复后再发下一条。比较的是整条业务路径，不是纯模型推理耗时。
- 相同的数字请求 2–11。新组在冒号后多一个空格；原始文字均保存，分组只忽略外层空白及该空格差异，因此不是字节完全相同的输入。
- 起点为 broker 本地入库，终点为微信 API 接受。手机显示时间没有逐条计时，实收由用户确认。
- 原生网关订阅及本机连接在采样时已就绪。微信发送连接在空闲达到 15 秒或发现关闭时于写前回收；没有逐条采集 TCP connection ID，不能把所有发送都称作热连接。
- 两组顺序采集，期间因修复发生中断，未做随机交替试验。结果仅代表本轮样本。

本轮 native send 前的样本 P95 为 **119.3 ms**，完整答复入队到微信发送开始的样本 P95 为 **43.5 ms**，低于 250/100 ms 目标。采用 nearest-rank；各 10 个样本的 P95 等于最大值，不能据此推断长期生产分位数。

## 初测异常与修复

修复前新链路初测到第 4 条时，爱丽丝已生成数字 5，但网关错误地把 `turn_trigger=chatgpt_messaging` 当成必需条件，过滤了合法的 `persistent_mode` 对外答复并推进游标。用户发现手机未收到。

已取消来源枚举限制，仍核对账号、dot、房间、对外角色、回复根和已知父消息；新增从未完成自有输入回填的机制。原来的 5 只补交一次，未重新提交给爱丽丝。169 项 Python 回归及 6 项 Node 检查通过。

初测原数据及恢复后的长延迟记录单独保留在本机私有报告，未丢弃、未混入上述修复后 10 条。旧链路 10 条基线完整保留。

## 当前部署

全部新纯文字使用直连，旧 MCP/Tunnel 保留查询和人工回滚能力。网关需要 Codex 桌面以本机调试入口保持运行；关闭桌面后排队重连，不自动转回 webhook。启动、状态、恢复与回滚命令见 [直连接入说明](DIRECT_GATEWAY.md)。
